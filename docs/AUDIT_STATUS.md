# Статус аудита Biddex

Обновлено: 2026-09-25 (M7, L6, L9 закрыты; приёмка товара покупателем; L4 — этапы 1–3). Бэкенд — этот репозиторий (`b2b-backend/`), фронтенд — репозиторий `Biddex-frontend` (`app.biddex.online`).

## Закрыто

**Критичные**
- **C1** — XSS через `imageUrl`/`jsAttr` в каталоге (фронтенд).
- **C2** — пополнение кошелька только для ADMIN (платёжного шлюза нет).
- **C3** — rate limiting по реальному IP клиента (`trust proxy 2` на Railway); счётчики логина/регистрации/восстановления работают.
- **C4** — переходы статусов RFQ; RFQ со ставками не редактируется; отмена — отдельным эндпоинтом с возвратом комиссий.
- **C5** — одна ставка поставщика на RFQ (+ уникальный индекс в БД).
- **C6** — платёж отмечается покупателем как PENDING, счёт и заказ меняет только подтверждение поставщика.

**Средние**: M1 (деактивация аккаунта), M2 (JWT недействительны после смены/сброса пароля), M3 (смена названия/CR снимает верификацию), M4 (анонимность покупателя до присуждения), M5 (отказ от LPO и повторное присуждение), M6 (машина состояний заказа), M7 (шортлист/отклонение/присуждение только для открытых ставок на RFQ в PUBLISHED/QUOTING_CLOSED, под блокировкой RFQ), M8 (дедлайны RFQ), M9 (атомарное списание комиссии), M10 (платежи под блокировкой счёта), M11 (доставка и заказ в одной транзакции), M12 (публикация RFQ только с бюджетом), M13 (номер LPO и контрагент в заказах), M14 (оплата остатка), M15 (просмотр документов админом, только PDF/изображения), M16 (ошибки `notify()` в Sentry), M17 (ошибки фоновых обновлений видны пользователю), M18 (правила email и паролей), M19 (обязательное согласие при регистрации).

**Низкие**: L1 (ошибки Prisma → 4xx), L2 (`Quote.currency` только BHD — CHECK в БД + проверка в API; статусы `LPO.CANCELLED`, `Payment.REFUNDED`, `WalletTxType.ADJUSTMENT`, `Invoice.dueDate`/`OVERDUE` оставлены намеренно для будущих функций), L3 (индексы на внешние ключи), L5 (вход не раскрывает существование/статус аккаунта), L6 (токен сброса хранится хешем; смена пароля — не больше 5 неверных текущих паролей за 15 минут на пользователя), L7 (удаление компании сохраняет записи контрагентов), L8 (DSN Sentry и `JWT_SECRET` только из окружения), L9 (уведомления и интерфейс: шортлист/отклонение ставки с уведомлением поставщику, в том числе проигравшим при присуждении; спор по заказу с причиной; раздел «Disputes» в админке — Resume/Cancel с комментарием в чат и уведомлением обеим сторонам; админ меняет заказ только через решение спора), L10 (кодирование токена в `verify.html`).

Также по ходу: **приёмка товара** — после отгрузки покупатель подтверждает получение (`POST /api/orders/:id/receipt`, `Order.receivedAt`, запись в чат, уведомление поставщику) или сообщает о проблеме (спор); оплата — только после приёмки (платежи, поданные раньше, поставщик может подтвердить); заказ COMPLETED только при приёмке и полной оплате; после приёмки спор закрыт. Суммы в филсах (`Decimal(12,3)`), BenefitPay, редактирование/отмена RFQ покупателем, раздел «Completed & cancelled» в LPO Management, начисление кредитов админом.

## Осталось

- **L4 (этапы 1–3 сделаны)** — выбрано приватное хранилище Railway Storage Buckets (S3-совместимое, `src/utils/storage.js`, переменные `S3_*`). Сделано: документы заказа (накладные, инвойсы, прочее; `OrderDocument`), загрузка через API (до 10 МБ, PDF/JPEG/PNG/WebP по содержимому), скачивание по presigned URL на 120 с только сторонам заказа и админу, мягкое удаление (объекты не перезаписываются и не удаляются). Этап 2: вложения к ставкам (`QuoteAttachment`, до 5 файлов по 10 МБ) — видят только поставщик, покупатель RFQ и админ (остальным 404, количество не раскрывается); менять можно, пока ставка SUBMITTED и приём ставок открыт; при принятии LPO вложения выигравшей ставки становятся документами заказа (`QUOTE_ATTACHMENT`, тот же объект в бакете). Этап 3: фото каталога и документы верификации — новые загрузки идут в бакет (серверная проверка `imageUrl`: только JPEG/PNG/WebP data URL до 2 МБ по содержимому); фото отдаются presigned-ссылкой (подписана на начало часа, действует 2 ч), документы — только админу, ссылкой на 120 с для просмотра; старые записи переносит `scripts/migrate-files-to-bucket.js` (см. «Перенос файлов в бакет»). На проде (2026-09-25) переносить было нечего: 0 товаров и 0 документов верификации, dry-run и `--verify` — 0 из 0; очистка data URL не нужна. Резервная копия бакета: ежедневная задача `scripts/backup-bucket.js` (cron-сервис Railway), восстановление — `scripts/restore-bucket.js` (см. «Резервная копия файлов»).

**Заметки по ходу**
- `verificationToken` хранится открытым текстом (риск ниже, чем у токена сброса).
- У админа нет кнопки «деактивировать компанию» — только удаление.
- Админ не получает уведомлений о новых спорах (у админа нет компании) — видит их во вкладке «Disputes», которая обновляется раз в 30 секунд.
- Причина спора хранится сообщением в чате заказа (префикс `Dispute opened: `), а не отдельной колонкой.
- Запись счёта создаётся при принятии LPO, но оплатить его можно только после приёмки; `Invoice.issuedAt` при приёмке ставится на время приёмки.
- Заказы, ставшие COMPLETED по предоплате до правила о приёмке, остаются COMPLETED (`receivedAt` пустой).
- Возвраты по отменённым оплаченным заказам не ведутся на платформе (деньги идут напрямую между компаниями).
- `embedded-postgres` для тестов — beta-версия (стабильной 17-й нет).
- Pre-deploy `prisma migrate deploy` в Railway не включён — миграции применяются вручную (см. ниже).

## Перенос файлов в бакет (L4, этап 3)

- Скрипт `b2b-backend/scripts/migrate-files-to-bucket.js`: без флагов — dry-run (ничего не меняет), `--apply` — перенос (data URL остаются, повторный запуск пропускает перенесённое), `--verify` — проверка файлов в бакете, `--cleanup` / `--cleanup --apply` — очистка data URL только у проверенных записей, `--clear-invalid-images` / `... --apply` — очистка `imageUrl`, которые не являются фото (ссылки и т.п.).
- Против прода: `.env.production` должен содержать `DATABASE_URL` и `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (из вкладки Credentials бакета). Переменные передаются только на одну команду:
  ```bash
  cd b2b-backend
  DOTENV_CONFIG_PATH=.env.production node -r dotenv/config scripts/migrate-files-to-bucket.js            # dry-run
  DOTENV_CONFIG_PATH=.env.production node -r dotenv/config scripts/migrate-files-to-bucket.js --apply
  DOTENV_CONFIG_PATH=.env.production node -r dotenv/config scripts/migrate-files-to-bucket.js --verify
  ```
  Скрипт печатает хост базы и имя бакета — проверить перед `--apply`.
- Выполнено на проде 2026-09-25 (миграция 6 и код выкачены; данных для переноса не было). Если старые data URL когда-нибудь появятся (например, из бэкапа), порядок: миграция `6_files_to_bucket` → выкатка кода → dry-run → `--apply` → `--verify` → проверка в интерфейсе → через несколько дней `--cleanup` (dry-run) → `--cleanup --apply`. После очистки код нельзя откатывать на версию до миграции 6 (старая версия не прочтёт документы без `fileUrl`).

## Резервная копия файлов

- Cron-сервис Railway `biddex-backup` (тот же репозиторий, Root Directory `b2b-backend`, Start Command `node scripts/backup-bucket.js`, Cron Schedule `0 23 * * *` UTC = 02:00 Бахрейн, Restart Policy Never, без домена и healthcheck). Переменные только у этого сервиса: `S3_*` (основной бакет), `BACKUP_S3_*` (резервный бакет в другом регионе), `SENTRY_DSN`; `BACKUP_RETENTION_DAYS` — по умолчанию 30.
- Каждый запуск: новые и изменённые файлы копируются под тем же ключом; удалённые из основного бакета и прежние версии изменённых хранятся в резервном под `_deleted/<дата>/<ключ>` 30 дней, потом удаляются. Если из основного бакета «пропало» больше 20% файлов (или он пуст) — ничего не переносится в корзину, тревога в Sentry. Ошибки — в Sentry с тегом `area: backup`; запуск с ошибками завершается с кодом 1. Sentry Crons, монитор `biddex-bucket-backup`: предупреждает о неудачном или пропущенном запуске.
- Восстановление с локальной машины (в `.env.production` нужны `S3_*` и `BACKUP_S3_*`):
  ```bash
  cd b2b-backend
  DOTENV_CONFIG_PATH=.env.production node -r dotenv/config scripts/restore-bucket.js                          # dry-run
  DOTENV_CONFIG_PATH=.env.production node -r dotenv/config scripts/restore-bucket.js --apply                  # недостающие файлы
  # --prefix <префикс> | --key <ключ> | --include-deleted (из корзины) | --overwrite (заменить отличающиеся)
  ```

## База данных и миграции

- **Прод-URL** хранится только в `b2b-backend/.env.production` (в git не попадает: `.gitignore` исключает `.env.*`, кроме `.env.example`). `b2b-backend/.env` указывает на **локальную** базу, поэтому команды по умолчанию до прода не достают.
- Команды против прода получают URL явно и только для одной команды:
  ```bash
  cd b2b-backend
  DATABASE_URL="$(node -e "require('dotenv').config({path:'.env.production'});process.stdout.write(process.env.DATABASE_URL)")" npx prisma migrate status
  ```
- Схема меняется только через `b2b-backend/prisma/migrations` (baseline `0_init` = схема прода на 2026-09-24, затем `1_l2_l3`, `2_order_status_before_dispute`, `3_order_received_at`, `4_order_documents`, `5_quote_attachments`, `6_files_to_bucket`). **`prisma db push` больше не используется.**
- **Railway**: Custom Start Command — `npm start` (до 2026-09-24 там был `prisma db push --accept-data-loss`, каждый деплой применял схему). Pre-deploy-команды нет.
- Порядок изменения схемы:
  1. изменить `schema.prisma`, локально `npm run migrate:new -- --name <что_меняем>`, прочитать и при необходимости поправить `migration.sql` (Prisma генерирует `DROP/ADD COLUMN` при смене типа — переписывать на безопасный `ALTER`);
  2. `npm test` — временный локальный PostgreSQL, `migrate deploy`, проверка совпадения со `schema.prisma`, интеграционные тесты; прод не трогается;
  3. на проде **вручную** `migrate deploy` (команда выше с `migrate deploy`) — **до** выкатки кода;
  4. выкатить код.
- Никогда не запускать против прода `prisma migrate dev`, `prisma migrate reset`, `prisma db push`.
- Точки восстановления — в Neon.
